# Runbook: ge_gerichte decision dates (2026-11-25)

**What is wrong.** Reported by Mnemosyne (Adrian König's agent) on 2026-11-09 (three DAS
rulings) and 2026-11-25 (ACJC/1085/2024). The Geneva scraper takes `decision_date` from the
official listing ("ACJC/1085/2024 du 03.09.2024"), which the ruling's header repeats, and
writes no `publication_date`. `scripts/repair_decision_dates.py --all` (one-off, 2026-03-12)
globbed every shard, ge_gerichte included although it is not on the pass's court list. It
took the listing date for a publication date, moved it into `publication_date`, put the
first date it found in the text into `decision_date` and stamped the row `date_extraction`
(`metadata_date` = the value it replaced). In a Geneva ruling that first date is procedural:

| chamber | what the pass took | example (served → ruling) |
|---|---|---|
| ACJC, CAPH | notification line above the header ("communiqué aux parties par plis recommandés du") | ACJC/1085/2024: 2024-09-11 → 2024-09-03 |
| DAS, DCSO | filing ("Recours … formé en date du") | DAS/192/2020: 2020-08-12 → 2020-11-18 |
| ACPR, DAAJ, AARP | decision under appeal ("contre l'ordonnance rendue le") | ACPR/680/2021: 2021-04-12 → 2021-10-13 |
| ATAS, ATA, JTAPI | a date from the facts ("Par décision du") | ATAS/527/2011: 2000-07-17 → 2011-05-24 |

The same happened to the entscheidsuche copies (`es_ge_gerichte.jsonl`). Rows scraped after
2026-03-12 carry no stamp and are fine.

**The fix.**

* `scripts/restore_ge_dates.py` plans both shards together and rewrites them together. A row
  is restored only when three values agree on one day: the date in the ruling's own head
  (`ge_header_date`: the first date between "POUVOIR JUDICIAIRE" and the parties or recitals;
  the notification line and the entscheidsuche preamble stand above the anchor), the stamp's
  `metadata_date`, and `publication_date`; and the header year is the year of the ruling
  number (the id's, or the one the text names). Then `decision_date` = that day and
  `publication_date` is cleared. Each changed row gets a `date_restore` stamp
  `{from, to, method: ge_header_date, at, publication_date: {from, to}}`; `date_extraction`
  stays. Everything else is unchanged and counted by reason.
* **Repeated ids.** `ge_gerichte.jsonl` holds 6,973 ids twice (each pair identical in date).
  The build inserts the first line and serves a repeat with another date as
  `<id>_dYYYYMMDD`, so every line of an id gets the same decision; the script refuses if two
  lines of one id would diverge.
* **Pass 1.** Direct rows (docket = ruling number) and es copies (docket = case number) never
  share a dedup key. One case number carries several rulings, so a restoration whose new key
  would make build Pass 1 delete a row whose text the kept row does not contain is held; the
  run refuses to write if any new loss remains (machinery of `restore_lu_dates.py`).
* `scripts/repair_decision_dates.py`: `ge_gerichte` and `es_ge_gerichte` added to
  `NEVER_REPAIR_SHARDS`, so a rerun of the 03-12 pass cannot redo it.
* Tests: `tests/test_restore_ge_dates.py` (offline, 21 tests; header shapes are the court's
  own, including the three that misled earlier rules: "Vu le jugement … du" in the Chambre
  civile summaries, "1 er mars", and a statute date in old DCSO heads).

**Rehearsal** (2026-11-26 ~00:00 UTC, on byte copies of both live shards pulled after the
11-25 incremental, sizes checked against the VPS):

| agrees (already right) | 1,323 | 1,153 |

37,425 distinct ids restored. Applied on the copies: only `decision_date`,
`publication_date` and `date_restore` differ, on exactly the restored lines; every other line
byte-identical, order kept; a rerun reports 0 changes (all `already_restored`). No restored
row has a federal docket; GE is in no overlap group and has no `_dYYYYMMDD` twins, so the
build's row count for ge_gerichte does not change (no swap-gate effect). Spot checks: the
four reported rulings, 12 random restored rows, 5 of the rows the HF count had missed
("1 er" headers), 8 rows released by the corrected year guard; all match the ruling's head.

**Not in this round** (left unchanged, for a second pass): 1,203 rows where the header and
the listing date differ (the listing date is 1–3 days later in 459, earlier in 253, weeks
apart in the rest), 1,022 rows without a readable head, and unstamped rows whose date is a
notification or rectification date (HF-mirror count: ~500 and ~2,900 candidates, not yet
sorted). Separately: every ruling published both directly and via entscheidsuche is served
twice (different dockets, no fold); that predates this repair.

## Deploy

1. Commit (`scripts/restore_ge_dates.py`, `scripts/repair_decision_dates.py`,
   `tests/test_restore_ge_dates.py`, this runbook), suite green, push, VPS ff-merge.
2. Window: after the 01:00 scrape has logged Done. and before the 03:30 build, or after the
   build has exited; never during the 20:00 incremental. Stop if any of these is not true:

   ```bash
   systemctl is-active opencaselaw-publish opencaselaw-publish-incremental opencaselaw-scrape
   ```
   (all three `inactive`), and the volume has ≥ 6 GB free (two temp files of 2.8 and 1.9 GB;
   the backups are hard links):
   ```bash
   df -h /mnt/HC_Volume_104655575
   ```
3. Dry run (≈ 75 s, ≈ 220 MB); expect the rehearsal's numbers plus whatever the scrapes added
   since (new rows are unstamped):

   ```bash
   cd /opt/caselaw/repo && ionice -c3 python3 scripts/restore_ge_dates.py \
       /mnt/HC_Volume_104655575/output/decisions/ge_gerichte.jsonl \
       /mnt/HC_Volume_104655575/output/decisions/es_ge_gerichte.jsonl --examples 10
   ```
   Stop if `pass1_lost_text_new` is not 0 or the restored counts differ from the rehearsal
   by more than a few rows.
4. Apply: the same command with `--apply`. Backups: `<shard>.bak-<UTC date>` (hard links,
   not `*.jsonl`). Rerun the dry run: `rows_changed` must be absent (0).
5. After the next build's swap, verify on the public API:

   ```bash
   for k in ge_gerichte_ACJC_1085_2024 ge_gerichte_DAS_192_2020 ge_gerichte_DAS_2_2017 ge_gerichte_DAS_228_2008; do curl -s "https://mcp.opencaselaw.ch/api/decisions/$k" | python3 -c 'import json,sys; d=json.load(sys.stdin); print(d["decision_id"], d["decision_date"], d.get("publication_date"))'; done
   ```
   Expect 2024-09-03, 2020-11-18, 2017-01-09, 2008-10-07, each with `publication_date`
   None; and `cite ACJC/1085/2024` → "vom 3. September 2024". The ge_gerichte count in
   `/health` must not drop.
6. Delete the two backups after the verification (checksum first), with Jonas's OK.

**Rollback.** Before the build: `mv <shard>.bak-<date> <shard>` for both shards. After it:
the same, then the next build serves the old dates again; or reverse per row from
`date_restore` (`from`, `publication_date.from`).
