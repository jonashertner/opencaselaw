# Runbook: lu_gerichte decision dates (2026-11-08)

**What is wrong.** Found 2026-11-08 by the TG/GE/SH identity session while checking LU
freshness. The Luzern scraper takes `decision_date` from the portal's own
"Entscheiddatum:" field (`gerichte.lu.ch/recht_sprechung/lgve/Ajax?EnId=<id>`) and writes
no `publication_date`. `scripts/repair_decision_dates.py --all` (one-off, 2026-03-12)
took that value for a publication date: it moved it into `publication_date`, put the first
"Urteil/Entscheid vom <date>" of the text into `decision_date` (in a Luzern ruling mostly
the decision under appeal) and stamped the row `date_extraction` (`metadata_date` = the
value it replaced). It did the same to the entscheidsuche copies in `es_lu_gerichte.jsonl`,
whose text opens with the portal's header ("Luzern Kantonsgericht 4. Abteilung 19.07.2013
V 13 31"). Rows scraped after 2026-03-12 are fine.

| EnId | docket | portal Entscheiddatum | served (2026-11-07 mirror) |
|---|---|---|---|
| 11092 | 7H 24 52 | 14.01.2025 | 2024-02-22 |
| 11096 | 7W 24 43/7W 24 44 | 08.07.2025 | 2020-07-01 |
| 11079 | 5V 24 280 | 19.05.2025 | 2016-06-29 |
| 10969 | 7Q 20 4 | 03.06.2022 | 2007-03-06 |

On the 2026-11-07 HF mirror, 1,191 of the 1,265 served direct rows have
`decision_date` != `publication_date`.

**The fix** (uncommitted, worktree `festive-mayer-71c1db`).

* `scripts/restore_lu_dates.py` plans both shards together and rewrites them together:
  * direct row, stamped, `publication_date` still equal to `date_extraction.metadata_date`
    (provably the scraper's portal value): `decision_date` = that value,
    `publication_date` cleared (the scraper writes none);
  * es copy, stamped, header date for its own docket == `metadata_date` ==
    `publication_date`: the same;
  * everything else unchanged. Each changed row gets a `date_restore` stamp
    `{from, to, method, at, publication_date: {from, to}}`; `date_extraction` stays.
  * **LGVE entries.** The portal publishes one ruling as several entries (EnIds 10968 and
    10969 are two Leitsätze of 7Q 20 4 of 3 June 2022). Build Pass 1 keys on
    court|docket|date and keeps only the longest row, so a correct date can make it
    delete a distinct entry. A restoration is held (row unchanged) when its new key would
    make Pass 1 delete a row whose text the kept row does not contain; the script
    computes Pass 1's losses before and after and refuses to write if any new one
    remains.
  * **Aliases.** Once a direct row and its es copy carry the same date, Pass 1 folds them
    and keeps the longer one (the es copy, which prepends header and Regeste to the same
    text). The kept row takes the dropped id as `previous_decision_id`
    (`previous_id_source: lu_date_fold`): the build records it in `decision_id_aliases`,
    `get_decision` resolves it, and the per-court swap gate counts it. Since f65d40a2
    (11-08) Pass 1 also records each id it drops (source `dedup_pass1`); both inserts are
    `INSERT OR IGNORE` and the `lu_date_fold` one runs first at insert time, so the two
    agree. The rehearsal below ran on a build without f65d40a2.
  * Dry run by default; `--apply` writes every `<shard>.tmp` first (only
    `decision_date`, `publication_date`, `date_restore`, `previous_decision_id`,
    `previous_id_source` may differ; same line count), refuses if a shard changed during
    the run, then hard-links each shard to `<shard>.bak-<UTC date>` (not `*.jsonl`) and
    swaps both in, one right after the other. Idempotent.
  * `--fetch-portal TSV` re-reads the portal (one request per second, resumable);
    `--portal TSV` makes re-read values win over the stamp (Fallnummer must still match).
* `scripts/repair_decision_dates.py` refuses `lu_gerichte` / `es_lu_gerichte`
  (`NEVER_REPAIR_SHARDS`), and LU is no longer listed among the courts whose
  `decision_date` is a publication date.
* `tests/test_restore_lu_dates.py`: 10 offline tests.
