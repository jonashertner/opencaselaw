# Runbook: Ticino decision dates from the ruling's own heading (2026-10-22)

**What is wrong (issue #90 part B).** Two production ids:

- `ti_gerichte_11.2016.86_d19921214` (source `entscheidsuche`, shard `es_ti_gerichte.jsonl`):
  served `decision_date` 1992-12-14 — the date of an Italian ecclesiastical tribunal
  ruling the text discusses ("Con sentenza del 14 dicembre 1992 il Tribunale
  ecclesiastico regionale emiliano di Modena ha annullato il..."), not the Lugano court's
  own ruling, which its heading states as "Lugano 24 gennaio 2018" and whose direct-scraper
  twin `ti_gerichte_11.2016.86` already correctly holds (2018-01-24).
- `ti_gerichte_14.2013.162_d20130913` (same source): served 2013-09-13, the date of the
  lower-court ruling under appeal ("con sentenza del 13 settembre 2013 (inc. n.
  SO.2013.2467) ha così deciso"), not this court's own ruling of "Lugano 24 gennaio 2014".

The `_dYYYYMMDD` suffix is minted at build time (`build_fts5.py` ~2094-2151) whenever an
incoming row's `(court, docket, date)` canonical key disagrees with the already-stored row
under the same `decision_id` — i.e. whenever the two shards disagree on the date for the
same docket.

**Root cause, both reported ids: `scripts/restore_ti_dates.py` has never been applied in
production** (no prior `ti_dates_*.md` runbook). Its existing `decide()` already classifies
both rows as `corrected` once simply run — the stored dates are themselves textually
confirmed (per `stated_in_text`) as other events' dates and the heading passes
`kopfzeile_disagrees`-free (for `11.2016.86`, the es Kopfzeile is 24.01.2018, matching the
heading; for `14.2013.162`, the es Kopfzeile is 24.01.2014, likewise matching). Confirmed
by running the unmodified script as a dry run against downloaded copies of both shards —
both ids land in the `corrected` bucket with the right target date.

**A second, narrower bug found and fixed in the same change.** 759 other `es_ti_gerichte`
rows hit `kopfzeile_disagrees`: the es Kopfzeile itself carries the wrong date (not just
the body text), blocking `heading_date()` even when the heading is good. Of those, 482
have a heading date that the **direct scraper's own twin row independently confirms**
(same docket, same date) — two independent sources agreeing should outrank a Kopfzeile
known to carry stale dates on some entscheidsuche copies. `heading_date()` / `decide()` now
take an optional corroborating date (`twin_date`, falling back to the row's own
`publication_date` only when the docket has no direct row at all; a docket whose direct rows
conflict is `AMBIGUOUS` and confirms nothing) and accept the heading when it agrees,
instead of refusing outright. `stated_in_text` additionally accepts a numeric `dd.mm.yyyy` /
`dd/mm/yyyy` form of the stored date, but only in the text after the heading: the es
Kopfzeile always carries the stored date, so reading it would make the "stored date must
appear in the text" guard vacuous.

After the fix (same copies): direct shard **unchanged** (fix never touches it — the
Kopfzeile pattern never matches direct-scraper text); es shard: `kopfzeile_disagrees` 759
→ 277 (−482), `agrees` +428, `corrected` 11,078 → 11,127 (+49), `stored_later_left_alone`
23 → 28 (+5). `rows_changed` for es: 11,127.

Applied on a second, disposable copy of both shards (never the originals): same counts as
the dry run exactly (deterministic); both reported ids verified to now hold 2018-01-24 /
2014-01-24 with a `date_restore` stamp; the 7,659 direct-shard changes are the script's
pre-existing, documented behaviour (it also corrects the direct scraper's own stored date
against the heading — unrelated to and unchanged by this fix) — flagged here, not a
regression.

**Dependency on the TI text re-fetch (added 2026-10-22, second pass).** The direct
`ti_gerichte.jsonl` has 15,140 rows the old extractor truncated (report 2026-10-14; fix:
`scripts/refetch_ti_gerichte_text.py`), and a fetch of the official pages was already run
on the VPS on 2026-10-15 into the sidecar `state/ti_gerichte.refetch.jsonl` (16,742
documents) — but that sidecar was never **applied** to the shard. Truncated text often cuts
off before the "Incarto n. … Lugano <date> … In nome della Repubblica" heading, so
`restore_ti_dates.py` sees `no_heading` on rows the re-fetch would fix. **Apply order
matters: refetch first, dates second** (per the 2026-10-15 design note: re-fetched texts
can open with a "Raccomandata" prefix, which `heading_date`'s un-anchored regex already
tolerates, see `test_heading_after_a_prefix_or_the_es_kopfzeile`).

Both reported ids confirmed correct in both shards after refetch+dates: `ti_gerichte_11.2016.86`
and `_14.2013.162` hold 2018-01-24 / 2014-01-24 in the direct shard (no `date_restore` needed —
already correct there) and in the es shard (`date_restore` stamped, same as before the refetch
pass — the refetch only touches the direct shard, so the es-side fix for these two ids is
unaffected by refetch ordering).

**Twin-suffix impact (simulated against `build_fts5.py`'s `(court, docket, date)` key via
`models.make_canonical_key`, not a full build).** Of 56,669 dockets shared by both shards:

| state | would mint a `_d` twin |
|---|---|
| before anything (production, as-is) | 7,211 |
| after refetch applied, dates not yet run | 7,211 (refetch alone changes only `full_text`, not `decision_date`) |
| after dates fix only (no refetch; first-pass rehearsal) | 2,539 |
| after refetch **then** dates fix (this order) | **1,912** |

Doing the refetch first unlocks headings in truncated direct-shard rows that
`restore_ti_dates.py` could not previously read at all, so running both in the intended
order removes 627 more twins than running the date fix alone (2,539 → 1,912). The
remaining ~1,912 are dockets where the two shards still disagree without heading evidence
to arbitrate (no heading even after refetch, future-dated heading, disagreeing Kopfzeile
with no corroboration, or a stored date later than the heading) — some may be genuine
distinct rulings under one docket (Zwischenverfügung/Endurteil), not all are bugs.

**Temp files (review 2026-10-23).** Both `restore_ti_dates.py` and `restore_vd_dates.py`
used to write their temp file as `tmpXXXX.jsonl` inside `output/decisions/`, and the build
ingests every `*.jsonl` there; an interrupt (Ctrl-C, ssh drop, disk full) left a duplicate
shard. They now write `.XXXXXXXX.jsonl.tmp` (hidden, not `*.jsonl`) and remove it in a
`finally`; tests cover a `KeyboardInterrupt` mid-write for each script. A SIGHUP still kills
Python without running the `finally`, hence the `systemd-run` and the leftover check below.

**Not in this runbook.** No scraper change; `ti_gerichte.py` and the entscheidsuche
ingestion are untouched. The refetch `fetch` phase (the slow, networked half) is not run
here — the sidecar already exists from 2026-10-15; only `apply` is rehearsed. Tests:
`tests/test_restore_ti_dates.py` (new cases for both reported ids, the twin-confirmation
rule, the publication_date fallback, a negative/ambiguous case, `load_twin_dates`, and the
numeric `stated_in_text` form); `tests/test_ti_gerichte_text.py` covers the refetch script
unchanged (its `--shard`/`--sidecar` flags already support pointing at copies).

## Apply

Steps 2 and 4 run under `systemd-run --unit=ti-dates-stepN --collect --wait --pipe` so an
ssh drop cannot kill them mid-write (alternative: `nohup ... > $B/stepN.log 2>&1 &`, then
`tail -f` the log).

One window, four steps in order (refetch apply, then dates apply — do not reorder):
after the 01:00 UTC scrape has logged `Done.` for `ti_gerichte` and before the 03:30 UTC
full build (`ti_gerichte.jsonl` is appended nightly by the scrape), or after a full build
exits and before the next scrape. `es_ti_gerichte.jsonl` and the sidecar are not touched by
the nightly scrape. Check immediately before:

```bash
ssh -i ~/.ssh/caselaw root@46.225.212.40 'date -u; systemctl show -p ActiveState --value opencaselaw-publish.service opencaselaw-scrape.service opencaselaw-publish-incremental.service; pgrep -af "build_fts5|run_scraper|publish.py" | grep -v pgrep || echo idle'
```

Backup both shards (the refetch step below rewrites `ti_gerichte.jsonl` in place):

```bash
ssh -i ~/.ssh/caselaw root@46.225.212.40 'set -e; cd /opt/caselaw/repo; D=/mnt/HC_Volume_104655575/output/decisions; B=/mnt/HC_Volume_104655575/quarantine/ti-dates-$(date -u +%Y%m%d); mkdir -p $B; cp -a $D/ti_gerichte.jsonl $D/es_ti_gerichte.jsonl state/ti_gerichte.refetch.jsonl $B/; ls -la $B'
```

**Step 1 — refetch apply, dry run** (uses the existing sidecar from the 2026-10-15 fetch;
no network, no `fetch` phase here):

```bash
ssh -i ~/.ssh/caselaw root@46.225.212.40 'cd /opt/caselaw/repo; python3 scripts/refetch_ti_gerichte_text.py apply --dry-run 2>&1 | tail -10'
```

Expect (rehearsal numbers, 2026-10-22; the live sidecar/shard may have grown slightly
since): `updated: 16,709`, `kept: 625`, `identity_mismatch: 12`, `no_sidecar: 42,331`. Stop
and investigate if `identity_mismatch` or `updated` differ by more than a few percent from
these — that means the sidecar or shard moved since the rehearsal.

**Step 2 — refetch apply:**

```bash
ssh -i ~/.ssh/caselaw root@46.225.212.40 'cd /opt/caselaw/repo; D=/mnt/HC_Volume_104655575/output/decisions; wc -l $D/ti_gerichte.jsonl; systemd-run --unit=ti-dates-step2 --collect --wait --pipe python3 scripts/refetch_ti_gerichte_text.py apply 2>&1 | tail -10; wc -l $D/ti_gerichte.jsonl; ls $D/*.tmp $D/.*.tmp 2>/dev/null'
```

Expect the same `updated: 16,709` and the shard rewritten (atomic replace, file mode kept).
The two `wc -l` counts must match and the final `ls` must print nothing (a leftover temp
file in `$D` would be ingested or at least litter the build input: remove it and investigate).

**Step 3 — restore_ti_dates, dry run** (now over the refetched direct shard + es shard):

```bash
ssh -i ~/.ssh/caselaw root@46.225.212.40 'cd /opt/caselaw/repo; D=/mnt/HC_Volume_104655575/output/decisions; python3 scripts/restore_ti_dates.py $D/ti_gerichte.jsonl $D/es_ti_gerichte.jsonl --examples 0 2>&1 | tail -20'
```

Expect `rows_changed` about 8,291 for `ti_gerichte` (vs. ~7,659 if the refetch step were
skipped — stop and check if it comes back closer to 7,659: that means step 1/2 did not
run) and about 11,127 for `es_ti_gerichte`.

**Step 4 — restore_ti_dates, apply:**

```bash
ssh -i ~/.ssh/caselaw root@46.225.212.40 'cd /opt/caselaw/repo; D=/mnt/HC_Volume_104655575/output/decisions; wc -l $D/ti_gerichte.jsonl $D/es_ti_gerichte.jsonl; systemd-run --unit=ti-dates-step4 --collect --wait --pipe python3 scripts/restore_ti_dates.py $D/ti_gerichte.jsonl $D/es_ti_gerichte.jsonl --apply --examples 0 2>&1 | tail -20; wc -l $D/ti_gerichte.jsonl $D/es_ti_gerichte.jsonl; ls $D/*.tmp $D/.*.tmp 2>/dev/null'
```

Post-check: the `wc -l` counts before and after must match per shard (the script rewrites
rows in place, it never adds or drops any) and the final `ls` must print nothing. stderr is
kept (`2>&1`) so a traceback is visible, not swallowed.

Rollback: copy the backups in `$B` back over the live shard paths (`ti_gerichte.jsonl`,
`es_ti_gerichte.jsonl`) and the sidecar — only inside the same window, before the next
scrape: the nightly scrape appends to `ti_gerichte.jsonl`, and restoring the backup drops
every row appended since it was taken (otherwise re-append that tail: the lines of the live
shard after the backup's line count, `tail -n +$((N+1))`); or, per row, read `date_restore.from` (and
`date_restore.prev` if restored more than once) and write it back as `decision_date`,
dropping the `date_restore` stamp — note this does not undo the text refetch (`full_text`,
`cited_decisions`), which has no rollback field of its own beyond the backup copy.
